# 初期プロトタイプの設計

## 目的

やることを整理し、行動する時間を確保し、実際に取り組んだことを残す。

タスク → 予定 → 実行 → 積み上げ → 振り返り、という日々の流れを扱います。

## データモデル

| データ | 主な項目 | 役割 |
| --- | --- | --- |
| Task | id, title, category, estimate, due, priority, done, doneAt, note, preferredStart, preferredEnd | やることと期限。estimateは見積もり時間（分）。 |
| Event | id, taskId, title, category, date, start, end, note, externalUid | 計画した時間。taskIdは任意。 |
| Log | id, title, category, date, minutes, note | 実際に取り組んだ時間（分）。 |
| Reflection | 日付をキーとする文章 | その日の気づき。 |

タスクを完了しても、見積もりを実績に自動加算しません。予定の変更で実行記録は変化しません。タスクを削除すると予定とのリンクだけを解除し、予定は保持します。

分野は試作では「学習・仕事・健康・暮らし」の4つです。

## 画面

- 今日：今日と期限超過のタスク、当日の予定、週の活動、集中タイマー。
- タスク：全タスクの検索・絞り込み・編集。
- スケジュール：月曜開始の週カレンダー。日本時間で0時から23時まで。
- 積み上げ記録：日付別の実行記録と振り返り、週集計、継続日数、16週間の活動表示。

継続日数は、記録のある連続した日数です。今日まだ記録がなければ昨日までの継続を表示します。同じ日に複数の記録があっても1日として数えます。

## 保存

バージョン1のJSONをlocalStorageに保存します。サンプルと個人データは別のキーです。バックアップの取り込みは内容を検証し、現在のデータを書き出してから置き換えます。読み込めないデータは上書きせず、設定から元の内容を保護できます。

## ユーザーの構想に合わせて決める項目

1. 積み上げの単位：時間、回数、成果、または組み合わせ。
2. タスク・習慣・長期目標の関係と階層。
3. 繰り返しタスク、繰り返し予定、予定変更の扱い。
4. ホームに最初に表示したい情報。
5. データベース、端末間同期、通知の必要性。

ここに記載した画面・分野・時間の単位は、最終要件ではなく初期プロトタイプの仮置きです。

## 入力と配置

日付・時・分はスクロールスナップを使ったホイールで選びます。所要時間は時間・分の2列です。遠い日付を直接入力する補助欄と、キーボード操作もあります。

タスクの希望時間帯は朝6–12時、午後12–18時、夜18–23時、自由指定。古いタスクは9–21時をデフォルトとして扱い、既存の保存データを変更せずに読み込みます。

仮配置は優先度と時間帯の狭さを考慮し、既存予定と新しい提案の両方を避けて、5分刻みで空き時間を探します。すでに予定のあるタスク・未来に期限があるタスクは対象から外し、配置できないタスクと理由を表示します。確定前にプレビューします。

## 連携

CSVは列マッピングを介してタスク・実行記録を追加します。JSONは全データの復元用です。ICSはイベントのUIDで追加・更新を判定します。削除と繰り返しの展開は扱いません。CSV・ICSの取り込み前には現在のデータをバックアップします。

Google Calendarの自動同期は未実装です。必要なSitesのアプリ連携利用確認が可能になった時点で、ユーザー認証、対象カレンダー、更新・削除の方向、競合時の扱いを設計します。

## データ資産とクラウド保存（v2）

タスクの状態と操作履歴を分け、完了の取り消し・アーカイブでも過去の記録を残します。旧データは日時の分かる精度で変換し、架空の時刻を付けません。NotionのZIPは標準DBの全列を選び、列の少ないビューを二重に取り込まないようにします。元CSVとページ本文も保管します。添付文書の指示は実行しません。

本番はSites認証済みのユーザーIDごとのD1保存です。APIは同一オリジンのJSON POST、データ形式、リビジョンを検証します。保存中のUnicode境界を保ち、現在とひとつ前のスナップショットを保持します。別端末の競合は確認するまで上書きしません。端末内データはキャッシュと通信不能時の控えです。

画面ソースはweb/、配置用Workerはworker/index.js、生成物はdist/です。データ形式の詳細はSCHEMA.mdにあります。

## スマホと独立運用

manifestとService Workerでホーム画面への追加とオフライン起動を扱います。キャッシュはビルドごとの画面用ファイルだけで、ログイン・API・ユーザー応答をキャッシュしません。HTMLとモジュールが別の版にならないよう、更新はインストール完了後に利用者が選んで反映します。記録の控えと未送信フラグは従来どおり端末へ残します。

独立版は同じ画面・API・データ形式を使い、Node.js 24・SQLite・サーバー内で検証する個人用パスワードセッションで動きます。外部から渡されたSitesユーザーIDは信用せず、検証済みセッションに対してのみ固定の個人IDを付けます。HTTPSではSecure・HttpOnly・SameSite=StrictのCookieを使用し、ログインと書き込みはOriginを検証します。セッションは期限・ログアウト・パスワード変更で失効します。

独立版のサーバー・ドメインは別途用意し、データは全データJSONで移行します。現在のSites版は所有者だけの公開範囲とSites認証を維持します。GoogleのOAuthを独立版に導入する場合は、公開ドメインとコールバックURLを確定してから設定します。
